# 笔记 ES 搜索与关键词高亮方案

## 背景

当前笔记列表接口位于 `little-note-server/src/main/java/com/lww/littlenote/service/impl/NoteServiceImpl.java`，`listNote` 目前只按当前用户和分组查询数据库，并按更新时间倒序返回。

`Note.content` 当前在数据库中加密存储。后续希望支持：

- 使用 Elasticsearch 搜索笔记标题和正文。
- 搜索结果支持关键词高亮。
- 数据库仍然保持加密存储，不改成明文。

## 成功标准

- 数据库 `note.content` 继续保存密文。
- ES 中保存可搜索的明文索引副本。
- 搜索必须按当前登录用户隔离，用户只能搜索自己的笔记。
- 支持按 `groupId` 过滤。
- 关键词命中标题或正文时，返回高亮字段给前端展示。
- 新增、修改、删除笔记后，ES 索引能同步更新。
- 后续可以支持全量重建索引，避免 ES 数据丢失或不同步后无法恢复。

## 关于前端加密和后端解密

如果现在是前端加密、后端可解密，这种方案不是绝对不行，但需要注意边界：

- 前端加密不能替代 HTTPS。前端代码和密钥很容易被查看，不能把它当作真正的端到端加密。
- 如果后端可以解密，说明后端就是可信处理方，搜索、索引、详情返回都应该由后端统一控制。
- 不建议让前端额外传一份明文给后端同步 ES，因为这样容易出现数据库密文和 ES 明文不一致，也更难校验数据来源。
- 更推荐后端在保存或同步时使用自己的解密能力得到明文，再写入 ES。

结论：数据库继续保存密文，ES 同步时由后端解密后写入 ES。这样数据源仍然以数据库为准，搜索索引只是派生数据。

## 重要安全取舍

ES 要做全文搜索和关键词高亮，必须能看到可分词的明文内容。因此，只要把正文写入 ES，ES 就会成为敏感数据存储。

需要接受并处理以下风险：

- ES 中的 `content` 是明文。
- ES 快照、备份、日志、排查工具都可能接触到明文。
- 如果 ES 被越权访问，笔记正文会泄露。

最低安全要求：

- ES 不暴露公网。
- 开启账号密码和 TLS。
- 应用连接 ES 使用最小权限账号，只允许访问笔记索引。
- 查询时后端强制使用当前登录用户 ID 过滤，不能信任前端传入的 `userId`。
- ES 备份和快照按敏感数据处理。

## ES 文档设计

建议新建笔记索引，例如：

```text
little_note_note
```

文档字段建议：

```text
id          笔记 ID，作为 ES document id
title       笔记标题，明文
content     笔记正文，明文，用于搜索和高亮
groupId     分组 ID
userId      用户 ID
createTime  创建时间
updateTime  更新时间
```

字段说明：

- `id` 使用数据库笔记 ID，便于覆盖更新和删除。
- `title` 和 `content` 用于全文搜索。
- `userId` 和 `groupId` 用于过滤，不参与评分。
- `updateTime` 用于排序。

中文分词可以使用 IK 分词器。如果暂时不引入 IK，也可以先使用 ES 默认分词器，但中文搜索效果会比较弱。

## 接口设计

### 请求参数

`NoteQueryReq` 建议新增：

```java
/**
 * 搜索关键词，为空时走普通数据库列表查询。
 */
private String keyword;
```

保留现有字段：

```text
pageNum
pageSize
groupId
```

`userId` 不建议继续由前端控制搜索范围。搜索时应始终使用 `SecurityUserUtils.getUserId()` 获取当前用户。

### 返回字段

`NoteVo` 建议新增：

```java
/**
 * 标题高亮内容，仅搜索结果中可能有值。
 */
private String highlightTitle;

/**
 * 正文高亮片段，仅搜索结果中可能有值。
 */
private String highlightContent;
```

不建议直接覆盖 `title` 或 `content`：

- 原始字段保持干净。
- 高亮字段只用于列表展示。
- 详情接口仍然返回真实正文内容。

## 查询流程

`listNote` 建议按是否存在关键词分流：

```text
keyword 为空：
  继续走当前数据库分页查询。

keyword 不为空：
  走 ES 搜索。
```

ES 搜索条件：

```text
filter:
  userId = 当前登录用户 ID
  groupId = 请求 groupId，存在时添加

query:
  title/content multi_match keyword

sort:
  updateTime desc

highlight:
  title
  content
```

这样普通列表不依赖 ES，只有搜索场景才使用 ES。ES 异常时，也不会影响无关键词的普通笔记列表。

## 同步流程

推荐使用数据库 outbox 表 + 定时任务同步 ES。原因是当前不要求很高实时性，搜索索引可以允许几秒到几十秒延迟；同时 ES 更新不应该影响笔记新增、修改、删除的主业务成功。

核心原则：

- 数据库是主数据源。
- ES 是可丢失、可重建的搜索副本。
- 业务接口只保证数据库写入成功。
- ES 同步失败不影响用户保存笔记。
- 后台任务负责重试和补偿。

建议新增索引任务表，例如 `note_index_task`：

```text
id            任务 ID
note_id       笔记 ID
action        操作类型：CREATE / UPDATE / DELETE
status        任务状态：WAIT / SUCCESS / FAIL
retry_count   重试次数
error_msg     最近一次失败原因
create_time   创建时间
update_time   更新时间
```

任务表只记录同步动作，不保存正文内容。处理 CREATE / UPDATE 任务时，后台任务重新从数据库读取最新笔记并解密 `content`，再覆盖写入 ES。这样即使同一条笔记短时间内多次修改，最终 ES 也会以数据库最新数据为准。

### 新增笔记

```text
1. 保存数据库密文。
2. 同一个数据库事务内写入 note_index_task，action = CREATE。
3. 定时任务扫描 WAIT/FAIL 任务。
4. 后台任务读取数据库最新笔记。
5. 后端解密 content。
6. 覆盖写入 ES 明文文档。
7. 标记任务为 SUCCESS。
```

### 修改笔记

```text
1. 更新数据库密文。
2. 同一个数据库事务内写入 note_index_task，action = UPDATE。
3. 定时任务扫描 WAIT/FAIL 任务。
4. 后台任务读取数据库最新笔记。
5. 后端解密最新 content。
6. 覆盖写入 ES 文档。
7. 标记任务为 SUCCESS。
```

### 删除笔记

```text
1. 删除数据库记录。
2. 同一个数据库事务内写入 note_index_task，action = DELETE。
3. 定时任务扫描 WAIT/FAIL 任务。
4. 删除 ES 文档。
5. ES 文档不存在时也按成功处理。
6. 标记任务为 SUCCESS。
```

## 定时任务处理规则

定时任务建议按固定频率扫描任务表，例如每 5 到 30 秒执行一次。当前不要求高实时性，可以先选择 10 秒左右。

处理规则：

- 每次只拉取一小批 `WAIT` 或可重试的 `FAIL` 任务，避免单次任务过重。
- 成功后标记 `SUCCESS`。
- 失败后增加 `retry_count`，记录 `error_msg`，状态标记为 `FAIL`。
- 超过最大重试次数后停止自动重试，保留记录便于人工排查。
- CREATE / UPDATE 使用数据库最新笔记覆盖写入 ES，保证幂等。
- DELETE 删除 ES 文档时，如果文档不存在，也认为成功，保证幂等。
- 如果处理 UPDATE 时数据库笔记已不存在，可以转为删除 ES 文档并标记成功。

实时性预期：

```text
用户保存笔记后，通常几秒到几十秒内可以被搜索到。
```

如果后续同步吞吐量明显上升，或者多个服务都需要消费笔记变更，再考虑升级为 MQ。当前阶段 outbox 表已经足够。

## 全量重建索引

需要提供一个内部使用的重建能力，用于：

- 首次接入 ES 时初始化历史笔记。
- ES 数据丢失后恢复。
- 修改索引 mapping 后重建。
- 修复历史同步失败的数据。

流程：

```text
1. 分页读取数据库中的笔记。
2. 后端逐条解密 content。
3. 批量写入 ES。
4. 记录失败数据，便于人工排查。
```

如果笔记数量不大，可以先做简单的管理接口或启动任务。后续数据量上来后，再改成异步任务。

## 推荐代码拆分

建议最小拆分如下：

```text
NoteServiceImpl
  负责业务入口和列表分流。

NoteEsService
  负责 ES 搜索、保存索引、删除索引。

NoteEsDocument
  表示 ES 中的笔记文档。

NoteIndexTask
  表示数据库中的 ES 同步任务。

NoteIndexTaskService
  负责创建任务、扫描待处理任务、更新任务状态。

NoteIndexSchedule
  定时触发任务扫描和 ES 同步。
```

这样可以避免把 ES 查询细节塞进 `NoteServiceImpl`，但也不需要做过度抽象。

## 实施顺序

1. 确认现有 `content` 的加密和解密入口。
   - 验证方式：后端能从数据库密文还原出正文。

2. 添加 ES 依赖和连接配置。
   - 验证方式：应用能创建 ES client，并能访问目标索引。

3. 创建 `NoteEsDocument` 和 `NoteEsService`。
   - 验证方式：可以手动保存、查询、删除一条笔记索引。

4. 创建 `note_index_task` 表和对应实体、Mapper、Service。
   - 验证方式：新增一条同步任务后，可以查询到 WAIT 状态任务。

5. 在新增、修改、删除笔记时，同一个事务内写入索引任务。
   - 验证方式：笔记业务成功后，任务表产生对应 CREATE / UPDATE / DELETE 任务。

6. 增加定时任务处理索引任务。
   - 验证方式：定时任务执行后，ES 文档对应新增、更新、删除，任务状态变为 SUCCESS。

7. 扩展 `NoteQueryReq` 和 `NoteVo`。
   - 验证方式：请求中可以传 `keyword`，响应中可以返回高亮字段。

8. 改造 `listNote` 搜索分流。
   - 验证方式：无关键词仍走数据库列表；有关键词走 ES，并返回高亮。

9. 增加全量重建索引能力。
   - 验证方式：清空 ES 后，可以从数据库重建完整索引。

## 暂不建议的方案

### 直接查数据库密文

不可行。密文无法做正常全文搜索，也无法做关键词高亮。

### 前端传明文给后端同步 ES

不推荐。前端传入的明文和数据库实际密文可能不一致，也绕开了后端的数据可信边界。

### ES 也保存密文

不适合当前目标。ES 如果看不到明文，就无法正常分词和高亮。

### 一开始就引入 MQ

当前没有必要一开始就引入 MQ。outbox 表是本方案的推荐实现，复杂度低于 MQ，并且比内存事件更可靠。

## 当前推荐结论

采用“数据库密文 + ES 明文索引副本”的方案。

普通列表继续查数据库；关键词搜索走 ES；ES 同步使用数据库 outbox 表 + 定时任务异步完成。高亮内容通过独立字段返回，避免污染原始标题和正文。

这个设计下，笔记保存、修改、删除只依赖数据库成功；ES 短暂不可用时不会影响主业务，后续由任务表重试补偿。数据库仍然是唯一可信数据源，ES 只是搜索副本。
